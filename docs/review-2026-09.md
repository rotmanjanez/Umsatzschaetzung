# Pre-release review: data model, storage, robustness

Status as of `c6cf476`. Scope: `Umsatzschaetzung.Core` (model, stores, calculation, service),
the app wiring and the Windows deployment policy. OCR, the tagger and the UI views were only
skimmed. The build and tests were **not** run (no .NET SDK available in the review environment).

The code is careful: integer money and quantities, deterministic tie-breaking, one file per
case, snapshots, migrations, a written Rechenweg. The problems below are about the *shape* of
the data. Every one of them gets much more expensive once the first case files and shared
`rules.db` files exist in the field.

## Top 5, in order

1. **A finished case cannot be reproduced.** Rules are edited in place and the case only
   references them by id. The report text says it prints the rule-set version and hash; it
   doesn't. → Keep rule history (append-only) and pin or freeze the rules a case used.
2. **One price and one VAT rate per product for the whole audit period.** Audits span several
   years, and in that time menu prices change and the food VAT rate changed several times
   (2020 16/5 %, 2021, 2024, 2026). The code also rejects 16 % and 5 % outright. → Model the
   periods explicitly.
3. **A shared `rules.db` on an SMB share, written by every installation.** SQLite locking over
   SMB is not reliable, and the "repair" path lets *one* client replace the shared file for
   everyone. → Don't write to a shared database directly. At minimum, never auto-restore a
   shared file.
4. **An ingredient's unit is implicit.** It is derived from whichever recipes use the
   ingredient, yet mapping factors and inventory counts are stored *in that unit*. →
   `Ingredient.Unit` as a real field.
5. **Lost updates everywhere.** The case is saved whole, with last write winning. Rules also
   save with last write winning, and validation runs outside the transaction. `MapCase` runs
   in the background and then saves a stale copy of the whole case. → Check versions
   optimistically (the `Rev` and `UpdatedAt` fields already exist).

## 1. Data model

### 1.1 Reproducibility: rules are mutable, cases only point at them (critical)

- `RuleStore.Put` is an `INSERT … ON CONFLICT DO UPDATE`, so the previous revision of a
  mapping, recipe or yield rule is gone. `Meta.Rev` records *that* something changed, not
  *what* it was.
- A case stores `InvoiceLine.MappingId` and `CaseProduct.ProductId`, `YieldChoice.YieldRuleId`.
  Every calculation runs against the rules as they are *now* (`LocalService.Compute` →
  `rules.Load()`).
  Consequence: someone fixes a crate factor from 20 to 24 bottles, and every closed case in the
  office silently changes its result. Deleting a mapping turns lines of old cases into
  "ungeklärt" (`RuleCheck.Users` can't see cases, so the delete is never refused).
- `docs/rechenweg.md` §7 and `bericht.html:472` state that the report carries "die Version und
  den Prüfwert (Hash) des verwendeten Regelsatzes". Nothing renders either. And `RuleSet.Version`
  is a local counter, so two installations can show the same number with different content.
- `CaseStore.Export` says the exported file is "in sich abgeschlossen", but without the rules
  it cannot be recalculated anywhere else.

**Recommendation (cheap now, very hard later):**

- Make rule rows **append-only**: `(id, rev)` as the primary key, with `deleted` as a revision
  of its own. "Current" becomes `max(rev)` per id. That gives history, audit trail and undo
  for free.
- Give each case a **frozen rule basis**. On "Abschluss / Bericht erzeugen", copy the rule
  revisions the calculation actually touched into the case file: mappings, ingredients,
  categories, products, yield rules, plus a content hash. Recalculating a closed case uses the
  frozen basis. "Auf aktuelle Regeln heben" is an explicit action that shows a diff. This also
  makes an exported case truly self-contained, which the court and the taxpayer's adviser
  will ask for.
- Print that hash and the app version in the report, or remove the sentence from the
  Rechenweg and the template.

### 1.2 Periods: one price and one VAT rate per product, one year for comparison (critical)

- `CaseProduct { GrossPrice, Vat }` holds one value for the whole period (`Model/Case.cs`).
  A Betriebsprüfung usually covers 3 years. Prices change, and restaurant food VAT was
  19→5 % (2020-07), 5→7 % (2021-01), 7→19 % (2024-01) and 19→7 % (2026-01); the standard
  rate was 16 % in 2020-H2. A mixed *price*
  can be defended (the Rechenweg admits this). A mixed *VAT rate* cannot: the output is
  "Umsatz je Steuersatz".
- `CaseStore.Validate` rejects everything except `0, 700, 1900`
  (`Casefile/CaseStore.cs:661`, `:675`), so 16 % and 5 % (2nd half of 2020) cannot be
  entered, although the Richtsatzsammlung 2020 ships with the app.
- `DeclaredRevenue` is per rate only, not per year. The Richtsatz comparison uses
  `c.PeriodTo.Year` alone (`Service/LocalService.cs:273`).
- `PeriodFrom` is validated and then never used. Invoices outside the period count fully
  (`Calc/Normalize.cs:33`), with no warning. Rule validity is checked against `PeriodTo` for
  products and yield rules, but against the invoice date for mappings. So a product that
  ended mid-period drops out entirely.

**Recommendation:** Decide now whether a case is one period or *n* sub-periods (usually the
Wirtschaftsjahre).

- Minimal version: `CaseProduct.Prices: [{ from, grossPrice, vat }]`, plus a date-valid VAT
  rate table as data instead of literals. Split revenue by the invoice date of the consumed
  goods, or by sub-period.
- Cleaner version: `Case.Periods: [{ from, to, declared[], inventory[], prices[] }]`. Run the
  calculation per period, compare each period with its own Sammlung year, and total across
  periods. Inventory (opening/closing stock) is naturally per year too.
- Either way, flag or exclude invoices outside `[PeriodFrom, PeriodTo]`.

### 1.3 The ingredient has no unit of its own (high)

`Scale.Of` derives an ingredient's base unit from every recipe that mentions it
(`Model/Scale.cs:7`). But `ArticleMapping.Factor` ("Inhalt eines Gebindes in der
Rezepteinheit") and `InventoryEntry` quantities are persisted *in that derived unit*.

- An ingredient without a recipe has no unit. Its lines all land in "unberücksichtigt", and a
  mapping factor can't even be interpreted.
- `RuleCheck.ValidateScales` only compares recipes with each other. Suppose the first recipe
  for an ingredient uses `g` while existing mappings were entered as pieces: every factor
  silently changes meaning.
- `Scale.Of` scans all products and runs for every invoice line (`Normalize.Run`) and in
  several other places, which is needless O(lines × recipe lines).

**Recommendation:** add `Ingredient.Unit` (`ml | g | piece`) as a required field. Validate
recipe units, mapping factors and inventory units against it. `Scale.Of` then becomes a field
read.

### 1.4 Integer amounts in the recipe unit are too coarse (medium)

`RecipeLine.Amount` is a `long` in the recipe unit, and the base unit for pieces is 1 piece.
Half a lemon, ½ bread roll or 0.5 g of saffron can't be expressed. Invoice quantities are
already in milli (`InvoiceLine.Quantity`). **Use milli-base-units throughout** (m-ml, mg,
milli-piece), or at least for `piece`. `Normalize.Convert` also truncates where it should
round (`line.Quantity * u.Factor / 1000`, `Calc/Normalize.cs:107`).

### 1.5 Suppliers are free-text names (medium)

Mappings match by article number only together with `m.SupplierName == supplier`, an exact
string (`Model/Rules.cs:155`). "METRO Deutschland GmbH", "Metro AG" and an OCR'd "METRO
Deutschiand" are three different suppliers. E-invoices carry the seller's USt-IdNr. (BT-31)
and often a GLN, which are stable keys.

**Recommendation:** a `Supplier` rule entity (`id`, `vatId`, `gln`, `names[]`). Invoices
resolve to a `SupplierId`, and mappings reference it.

### 1.6 Machine guesses go straight into the shared rule base (medium)

During import, `MapLine` saves any suggestion with confidence ≥ 80 as a new, unconfirmed
mapping in the **shared** `rules.db` (`Service/LocalService.cs:360-368`). Every user's imports
therefore grow the common rule set. Other users' cases then use those guesses, only flagged
as "unbestätigt". Combined with 1.1, a case's result depends on what colleagues imported
later.

**Recommendation:** keep unconfirmed suggestions **in the case** (on the line: suggested
ingredient and factor, confidence). Promote them to a shared mapping only on confirmation.

### 1.7 Smaller model points

- **Denormalised totals.** `Invoice.NetTotal/GrossTotal` are "the sum of the positions" but
  are stored, and only recomputed for scans. Compute them instead.
- **Rates as magic literals.** `Bp.Full` exists, but `0/700/1900` literals are spread over
  `CaseStore.Validate` and `VatRow.Rates`. They belong in one table (see 1.2).
- **`YieldChoice` / `YieldRule`** use either an ingredient id or a category id, as two
  nullable strings. That is fine, but enforce it with a `CHECK` in SQL too (see 2.2).
- **`Case.Taxpayer.Gewerbe`** is a free string checked against a regex. Validate it against
  the known Kennzahlen of the Sammlungen, so a typo doesn't silently turn off the Sparten
  split (`Gewerbe.Gastronomie`) or the comparison.

## 2. Data layout / storage

### 2.1 Shared `rules.db` on a network share (critical)

The ADMX policy explicitly offers a UNC path "in der alle Installationen die gemeinsamen
Regeln … ablegen". Issues:

- **SQLite over SMB.** File locking on network file systems is unreliable (SQLite's own FAQ).
  Concurrent writers can corrupt the file. Every installation writes at **every start**:
  migration check, `SeedRules`, `SeedSammlungen` and a `VACUUM INTO` snapshot
  (`Rulestore/RuleStore.cs:107-114`).
- **Auto-restore on a shared file.** If `quick_check` fails *for one client*, and on SMB that
  can be transient, that client moves the shared `rules.db` aside and copies in the newest
  snapshot (`RuleStore.Restore`). Everyone's edits since that snapshot are silently dropped.
- **Snapshot rotation.** Only 10 snapshots are kept, one per start. With 30 users that is
  about an hour of history, so the "backup" may already contain the damage.
- **Derived data on the share.** `embeddings.db` (a pure cache) also sits on the share
  (`new EmbeddingStore(rules.Dir)`), with multi-writer access and no benefit.
- **Mixed versions.** A newer client migrates the shared schema, and every older client in
  the office then fails to start (`SchemaTooNewException`).

**Recommendation, from least to most work:**

1. Now: never auto-restore a store that is not local. Show the problem and stop instead. Move
   `embeddings.db` to local app data. Snapshot only after a write, not at every start. Keep
   snapshots by age (daily/weekly), not by count.
2. Better: each installation works on a **local copy** and syncs rule changes as
   append-only revision files, e.g. `changes/<install-id>/<rev>.json`, merged by
   `(id, rev, changedAt)`. With 1.1 in place, this is natural: revisions are immutable, so a
   merge is a union.
3. Or: a tiny server (the `IService` comments already sketch the REST routes) owns
   `rules.db`.

### 2.2 No referential integrity in either schema (high)

No `FOREIGN KEY`, no `CHECK`, `PRAGMA foreign_keys` never enabled. Symptoms:

- **Orphaned documents and readings.** `CaseStore.Save` deletes and rewrites the case tables
  but not `document` / `reading_*` (`Casefile/CaseStore.cs:148`). An invoice removed any other
  way than `DeleteInvoice` leaves its document behind, and the document travels with every
  export. That is a GDPR issue for a tax tool. `DeleteInvoice` itself does `SaveCase` and
  then `DeleteFile` in **two** transactions.
- In `rules.db`, a `recipe_line` can point to a deleted ingredient, and `category_gewerbe` can
  outlive its category. Integrity is enforced only in C# (`RuleCheck`), and only for the
  rules as loaded in that moment (see 3.2).

**Recommendation:** since it is pre-release, **squash the migrations into one baseline**
(the RuleStore data-patch migration #3 with hard-coded ids shouldn't survive into 1.0).
Add `FOREIGN KEY … ON DELETE CASCADE` (invoice → lines → document → reading) and `CHECK`s
for enums, non-negative amounts and either/or columns. Enable `PRAGMA foreign_keys=ON` on
every connection.

### 2.3 OCR reading: 7 tables for a write-once blob (medium, simplification)

`reading_page/word/header/line/cell/page_flag/line_flag` normalise the scan result into seven
tables, and duplicate the invoice-line columns (`LineColumns` is used for both). The reading
is written whole and read whole, never queried. **Store it as one row per invoice**:
`reading(invoice_id PK REFERENCES invoice ON DELETE CASCADE, format INT, data BLOB)`, using
the JSON you already serialise with `ModelJsonContext` (compress it if you like). That
removes about 150 lines, and changes to `OcrPage` no longer need a schema migration.

The same argument applies to the **Richtsatz tables** in `rules.db` (7 tables, ~150 lines of
mapping code). That data is read-only reference data, shipped as JSON. Read the embedded JSON
directly, and store a user-imported year as one JSON blob. It doesn't belong in the mutable,
shared, snapshotted database.

### 2.4 Unstable encodings in the file format (medium)

The same enums are persisted three different ways:

- `Source` and `Field` are written with `ToString()` and read with `Enum.Parse`
  (`CaseStore.cs:322`, `:447`, `:464`). So the **C# member name** is the file format:
  renaming `Ubl` breaks every case file.
- `Sparte` uses a hand-written mapping (`"getraenke"`).
- JSON uses `JsonStringEnumMemberName` (`"ubl"`).

Use one explicit code per member everywhere (the JSON names are good). Case files are
long-lived evidence: define their format as a contract and add a format-version test that
opens a checked-in v1 file.

### 2.5 Seed data can never be updated (medium)

`SeedRules` inserts only ids that don't exist yet (`RuleStore.cs:401`), and soft-deleted rows
count as existing. A corrected recipe, a better alias list or a fixed yield rate in
`seed.json` will never reach an installed base. **Record the origin per row** (`seed@<date>`
vs. `local`). On start, update rows whose current revision is still the seed revision, and
leave locally edited rows alone. This fits 1.1 directly.

### 2.6 Whole-case rewrite per save (low)

Every `PutCase` deletes and re-inserts all rows, including every invoice line. That is fine
for correctness (a single transaction), but it is what makes 3.1 possible, and it gets slow
with many invoices. If you keep the relational layout, move towards granular commands
(`SetPrice`, `SetLineMapping`, …). The service interface is already halfway there.

## 3. Robustness

### 3.1 Lost updates on cases (high)

- `MapCase` loads the case, awaits the matcher on a background thread (seconds), then saves
  the whole case (`LocalService.cs:240`). A price edited in `CalcView` in the meantime is
  overwritten.
- `Attach` (import/verify) and `DeleteInvoice` also do load → modify → save.
- The instance lock *allows* a second window after a prompt. Two windows on one case silently
  overwrite each other.

**Fix:** `CaseStore.Save(c, expectedUpdatedAt)` compares inside the write transaction and
throws `Conflict`. The UI reloads, or asks. It's about 10 lines.

### 3.2 Lost updates and TOCTOU on rules (high)

- `SaveRule`: `rules.Load()` → `RuleCheck.Validate` → `rules.Save(rule)` are three separate
  steps (`LocalService.cs:47-48`). Validation runs on a snapshot outside the write
  transaction. User A deletes an ingredient while user B saves a mapping to it, and both
  succeed.
- `Meta.Rev` travels to the client but is never compared, so an edit made on a stale rule
  overwrites a colleague's newer revision. The instance-lock dialog text already describes
  this bug.

**Fix:** in `RuleStore.Save`, open the `IMMEDIATE` transaction, read the rule set inside it,
validate, check `rev = expected`, then write. Fail with `Conflict` otherwise. Do the same for
`Delete`, including the `Users` check.

### 3.3 Smaller robustness points

- **`Guard` catch-all.** Any unexpected exception in the calculation becomes
  `ErrorCode.Invalid "Kalkulation: …"` (`LocalService.Compute`). A bug then looks like bad
  user input. Keep `Internal` for non-domain exceptions, and log them.
- **`CaseStore.List` fails whole.** One unreadable `.db` in the case folder throws, and the
  whole case list fails. Skip the file and report it instead.
- **Unchecked arithmetic.** `Calc` uses `long` without `checked`, apart from a catch for
  `OverflowException` around the knapsack. The current magnitudes are OK (roughly ≤1e15), but
  a `checked` context in `Calc/` costs nothing and turns a silent wrap into an error.
- **Case-file backups pile up.** `.v{n}.bak` copies are left next to case files forever, and
  `Delete` doesn't remove them.

## 4. Suggested order

| # | Change | Effort | Why now |
|---|--------|--------|---------|
| 1 | Squash migrations to one baseline; add FKs/CHECKs, stable enum codes, reading as JSON blob | S–M | Last chance without migration code |
| 2 | `Ingredient.Unit`; milli base units | S | Changes the meaning of stored factors |
| 3 | Optimistic concurrency for cases and rules; validate inside the transaction | S | Real data loss today |
| 4 | Append-only rule revisions; seed origin per row | M | Needed by 5 and 6 |
| 5 | Frozen rule basis per case, and its hash in the report | M | Core promise of the Rechenweg |
| 6 | Periods: prices/VAT by date, VAT table as data, per-year comparison, out-of-period invoices | M–L | Domain correctness, and case-file format |
| 7 | Shared store: no auto-restore on shares, local embeddings, then sync or a server | S → L | Corruption risk at the first multi-user site |
| 8 | Supplier entity; unconfirmed suggestions kept in the case | M | Rule-base hygiene |

Items 1–3 are mostly mechanical. Items 4–6 are the real design decisions, and they are the
ones that get expensive once case files exist.
